# Club Calendar for iOS

The iOS app syncs your Strava club events into Apple Calendar, the same as the
macOS menu-bar app. Both apps are thin platform shells over a shared
`ClubCalendarCore` Swift package, so the Strava, Calendar, Auth, and Sync logic
is identical across platforms — only the UI and the OS-integration plumbing
differ.

- **Minimum OS:** iOS 26.0
- **Language / tools:** Swift 6.2, SwiftUI, Xcode 26
- **Bundle ID:** `com.clubcalendar.ios` · **Swift module:** `ClubCalendarIOS` ·
  **product/​`.app`:** `ClubCalendar`
- **Third-party runtime deps:** none (ViewInspector is test-only)

For getting the app onto a physical iPhone (signing, trust, 7-day reinstall),
see **[ios-install.md](ios-install.md)** — this document is about how the app is
built and how it works.

---

## Features

- **Today** — every upcoming club event in the next 30 days, grouped by day
  (Today / Tomorrow / weekday). Tap a row to open the event on Strava.
- **Clubs** — the clubs you've joined on Strava; toggle which ones sync.
- **Settings** — Strava connection, sync interval, appearance
  (System / Light / Dark), last-sync status, and a log export for diagnostics.
- **Onboarding** — a four-step wizard: API credentials → connect → pick clubs →
  calendar access.
- **Background sync** — opportunistic `BGAppRefreshTask`, plus a foreground
  catch-up sync every time the app becomes active so the UI is always current.

## Architecture

Both apps wire the same `ClubCalendarCore` services through their own
composition root. On iOS that root is `AppState`:

```
ClubCalendarApp (SwiftUI @main)
  └── AppState (@MainActor @Observable)
        ├── KeychainHelper        (Security.framework — data-protection keychain)
        ├── AppSettings           (@AppStorage + JSON-encoded clubs)
        ├── StravaService (actor) (api.strava.com — tokens + clubs + events)
        ├── CalendarService (actor) (EventKit; dedup by Strava ID in EKEvent.url)
        ├── AuthService           (ASWebAuthenticationSession, clubcalendar:// scheme)
        └── SyncService           (drives Strava → Calendar; iOS uses BGAppRefreshTask)
```

`AppState` is the only iOS-specific glue; everything below it is shared. It
exposes observable UI state (`upcomingEvents`, `isAuthenticated`,
`calendarAccessStatus`, `isLoading`, `errorMessage`, …) and forwards user
actions to the services. Tests inject a `MockKeychainHelper` (and optionally an
isolated `CalendarService`) through its designated initializer.

### Sync flow

```
SyncService.sync()
  → StravaService.getEventsForClubs(enabledClubIds)
  → CalendarService.syncEvents(events)        # create / update / [CANCELLED]
  → posts .syncDidComplete
```

`AppState` observes `.syncDidComplete` and reloads `upcomingEvents`, so a
background sync refreshes the visible list without going through `AppState.sync()`.

### Foreground vs background sync

iOS has no always-running process, so syncing happens two ways:

- **Foreground (reliable).** On launch (`.task`) and on every return to the
  foreground (`scenePhase == .active`), `AppState` runs `syncService.syncIfStale()`
  — a sync gated by the user's chosen interval. This is why the UI is always
  fresh when you open the app.
- **Background (best-effort).** `BackgroundSyncCoordinator` registers a
  `BGAppRefreshTask` (identifier `com.clubcalendar.sync`) at launch and submits a
  request with `earliestBeginDate = now + interval` whenever the app
  backgrounds or a run finishes. iOS treats this as a hint, not a guarantee, and
  may delay or skip it based on usage. The handler reschedules first (so a hung
  sync still gets another shot), runs `SyncService.sync()`, and reports success.

`BGTaskScheduler.register` throws if called twice in a process, so registration
is guarded by a `didRegister` flag (this also lets the test host construct the
app more than once).

### Authentication

`AuthService` runs Strava OAuth through `ASWebAuthenticationSession` with the
custom scheme `clubcalendar`. The redirect URI is `clubcalendar://callback`.

> **Strava setup:** the API application's **Authorization Callback Domain** must
> be `callback` — a bare host with no scheme or slashes — because Strava matches
> it against the *host* of the redirect URI. This is the most common reason
> connecting fails (`redirect_uri invalid`). One Strava app serves both
> platforms. See README setup and [ios-install.md](ios-install.md).

`ASWebAuthenticationSession` intercepts the redirect via its `callbackURLScheme`,
so no `CFBundleURLTypes` registration is strictly required (one is present
anyway). The presentation anchor resolves the foreground `UIWindowScene`.

### Keychain + entitlements

Credentials and OAuth tokens live in the iOS data-protection keychain via
`KeychainHelper` (shared with macOS). The data-protection keychain requires the
app to own a **keychain access group**; without one, `SecItemAdd` fails with
`-34018` (`errSecMissingEntitlement`). So:

- `ClubCalendar.entitlements` declares
  `keychain-access-groups = [$(AppIdentifierPrefix)com.clubcalendar.ios]`, wired
  via `CODE_SIGN_ENTITLEMENTS` in `project.yml`.
- Simulator builds are **ad-hoc signed** (`make` sets `CODE_SIGN_IDENTITY="-"`)
  rather than unsigned, so the entitlement is actually embedded. Unsigned builds
  (`CODE_SIGNING_ALLOWED=NO`) hit `-34018` the moment they touch the keychain.

### Settings & persistence

`AppSettings` (`@MainActor @Observable`) stores everything in `UserDefaults` via
`@AppStorage`: `syncIntervalMinutes`, `calendarName`, `maxMenuEvents`,
`onboardingCompleted`, `appearanceMode`, and the JSON-encoded `syncableClubs`.
`appearanceMode` (`system` / `light` / `dark`) is read directly by
`ClubCalendarApp` via `@AppStorage` and applied with `.preferredColorScheme`, so
changing it in Settings updates the whole app live.

> **Note:** `maxMenuEvents` is a macOS menu-bar concern. iOS deliberately shows
> *all* events in the window (`getUpcomingEvents(limit: .max)`), so the
> "events shown" control is not surfaced on iOS.

## Build, run, and test

All commands assume the repo root. Override the simulator with
`IOS_SIM_DEVICE='iPhone 17 Pro'`.

```bash
make ios-gen        # regenerate the Xcode project from project.yml
make ios-build      # build for the simulator (ad-hoc signed)
make ios-run        # build + boot simulator + install + launch
make ios-test       # xcodebuild test on the simulator, with coverage
make ios-coverage   # print the coverage report after ios-test
make ios-logs       # stream unified logs (subsystem com.clubcalendar.app)
make ios-clean      # remove iOS build artifacts
```

`make ios-test` pre-grants Calendar permission to the simulator
(`xcrun simctl privacy … grant calendar`) so `requestFullAccessToEvents()`
returns granted without a UI prompt and the real-EventKit integration tests can
write to the store.

### Testing approach

- swift-testing (`@Test` / `@Suite`) throughout.
- The real keychain isn't reliably available to unsigned test bundles, so tests
  inject `MockKeychainHelper`. `AppSettings.shared` and the keychain are wiped
  between suites by `TestHelpers`.
- `CalendarServiceIntegrationTests` exercises a live `EKEventStore`, using a
  uniquely-named calendar per test so it never collides with the app's real
  "Club Calendar" calendar; it skips cleanly when Calendar access isn't granted.
- `ViewTests` mount each view via `ViewInspector`'s `ViewHosting` to execute
  every state branch; assertions are deliberately light (the new Observation
  macro defeats structural inspection).

## Configuration reference

Declared in `project.yml` (and emitted into the generated `Info.plist`):

| Key | Value | Why |
| --- | --- | --- |
| `NSCalendarsFullAccessUsageDescription` | calendar usage string | EventKit full access (iOS 17+ key) |
| `CFBundleURLTypes` → scheme | `clubcalendar` | OAuth redirect scheme |
| `BGTaskSchedulerPermittedIdentifiers` | `com.clubcalendar.sync` | must match `BackgroundSyncCoordinator.taskIdentifier` |
| `UIBackgroundModes` | `fetch` | enables `BGAppRefreshTask` |
| `CODE_SIGN_ENTITLEMENTS` | `ClubCalendar.entitlements` | keychain access group |
| `PRODUCT_MODULE_NAME` | `ClubCalendarIOS` | mirrors SPM's `ClubCalendarMac` |

`PrivacyInfo.xcprivacy` declares no tracking/collection and the `UserDefaults`
required-reason API (`CA92.1`) for `@AppStorage`.

## App icon

The icon is the white "cc" calendar mark (the same artwork as the macOS
menu-bar glyph, `icon/icon.png`) on a deep indigo→navy gradient. Regenerate it
with:

```bash
./icon/build-ios-appicon.sh    # needs ImageMagick; writes the 1024px AppIcon
```

iOS app icons must be opaque (no alpha channel), which the script enforces.

## Maintenance & troubleshooting

- **Install / 7-day reinstall / device trust:** [ios-install.md](ios-install.md).
- **"redirect_uri invalid" or no events sync:** check the Strava Authorization
  Callback Domain is `callback` (see Authentication above).
- **`-34018` keychain error:** the build wasn't signed with the keychain
  entitlement — use the `make` targets (which ad-hoc sign), not a raw
  `CODE_SIGNING_ALLOWED=NO` build.
- **Background refresh seems unreliable:** expected; iOS schedules it
  opportunistically. The foreground catch-up sync keeps the UI fresh.
